1. ARCHITECTURE CONTEXT & INGESTION FLOW
================================================================================
CodeSpec AI ingests code repositories (via Git clone or ZIP upload) and constructs
a multi-layered code intelligence backend combining:
  1. Structural Code Knowledge Graph (Neo4j): AST entities, call graphs, imports,
     type hierarchies.
  2. Dense RAG Engine: Semantic retrieval across all repository contents (source
     code, markdown docs, architecture PDFs, configs, plain text).

Prior to Phase 1:
  - Repositories were fetched via GitFetcher or ZipHandler to REPO_WORKSPACE_DIR.
  - RepoScanner.scan() scanned only supported source code extensions (.py, .js, .ts, etc.).
  - ParserRegistry parsed source files with Tree-sitter.
  - GraphBuilder loaded symbols into Neo4j.
  - Non-source files (READMEs, specs, configs, PDFs) were ignored, and no file
    classification existed for downstream RAG.

Phase 1 Goal:
  Extend the repository ingestion pipeline so that every file in the repository
  is normalized and classified into structured categories before downstream RAG
  processing, while strictly preserving existing AST and Neo4j graph operations.

2. PHASE 1: REPOSITORY CONTENT CLASSIFICATION & FILTERING [STATUS: COMPLETED]
================================================================================

2.1 Objectives & Deliverables
------------------------------
  - Add a clean file classification and filtering layer.
  - Classify files into 6 canonical categories:
      * source_code
      * markdown
      * pdf
      * plain_text
      * config
      * unsupported
  - Ignore generated, vendor, and binary content:
      * .git, node_modules, .venv, __pycache__, dist, build, coverage, etc.
      * Binary/executable files (.exe, .dll, .so, .bin, .pyc, .zip, media, etc.)
  - Make extension handling configurable rather than hardcoded throughout the code.
  - Preserve rich metadata for every processable file:
      * repository_id
      * file_path (normalized with forward slashes)
      * file_name
      * extension
      * language (when applicable)
      * file_type
      * size_bytes
      * is_processable
  - Preserve all existing repository ingestion behavior with zero regressions.
  - Add comprehensive unit tests.

---------------------------------------

A. Typed Models & Schemas (app/models/classification.py):

     1. Checks if any directory part is in ignored_directories.
     2. Checks if path.name is in ignored_files.

D. Classification Engine (app/core/ingestion/classifier.py):
   - FileClassifier class:

     * scan_and_classify(root_dir, repository_id) -> RepositoryClassificationResult:
       Returns full classification result container.

F. Celery Ingestion Pipeline Integration (app/workers/tasks.py):
   - Updated _run_pipeline(repo_dir, repo_url, repo_name, branch):
     * Runs _scanner.scan_and_classify() to classify all repository files.
     * Logs classification counts.
     * Runs _scanner.scan() to pass source code paths to ParserRegistry and GraphBuilder.
     * Returns pipeline result dictionary with new classification fields while
       strictly preserving all previous keys:
       {
         "repo_url": repo_url,
         "repo_name": repo_name,
         "branch": branch,
         "files_scanned": len(file_paths),
         "files_parsed": len(summaries),
         "files_classified": classification_res.summary.total_files_scanned,
         "processable_files": classification_res.summary.processable_files,
         "classification_summary": classification_res.summary.counts_by_type,
         **stats,

3. PHASE 2: MULTI-FORMAT CONTENT PARSING [STATUS: COMPLETED]
================================================================================

3.1 Objectives & Deliverables
------------------------------
  - Convert supported repository files (classified in Phase 1) into a unified,
    normalized document representation for RAG while preserving rich format-specific
    source metadata.
  - Implement format-specific parsers for:
      * 1. Source code (Python, TypeScript, JavaScript, Java, Go, C#, C++, etc.)
      * 2. Markdown (.md, .markdown, .mdx)
      * 3. PDF (.pdf)
      * 4. Plain text (.txt, .text, .log, .rst)
      * 5. Configuration files (.json, .yaml, .toml, .ini, .cfg, Dockerfile, Makefile)
  - Key Requirements Fulfilled:
      * Reuse Phase 1 file classification (ClassifiedFile, FileType).
      * Preserve PDF 1-indexed page numbers.
      * Preserve Markdown hierarchical heading and section breadcrumbs.
      * Preserve source code AST symbol IDs, class/method boundaries, and line spans.
      * Preserve config format and structured key metadata.
      * Keep parsing library choices isolated behind parser interfaces.
      * Handle empty, unreadable, malformed, and binary files gracefully without
        crashing repository ingestion.
      * Store parser errors as structured metadata.

3.2 Components & Implementation Details
---------------------------------------

A. Normalized Document Schema (app/models/rag_models.py):
   - NormalizedDocument(BaseModel):
       * repository_id: str
       * file_path: str (normalized with forward slashes)
       * file_type: FileType
       * language: Optional[str]
       * content: str (extracted code/text block)
       * start_line: Optional[int]
       * end_line: Optional[int]
       * page_number: Optional[int] (1-indexed, for PDFs)
       * section: Optional[str] (e.g. heading breadcrumb, class/function scope, config key)
       * symbol: Optional[str] (e.g. AST symbol ID 'path::ClassName::methodName')
       * metadata: dict[str, Any] (docstrings, parameters, return types, total pages)
   - ParserError(BaseModel):
       * file_path: str
       * error_type: str (e.g. 'FileNotFound', 'EmptyFile', 'ReadError', 'PdfReadError', 'SyntaxWarning')
       * message: str
       * timestamp: str (ISO format)
   - ParseResult(BaseModel):
       * file_path: str
       * documents: list[NormalizedDocument]
       * errors: list[ParserError]
       * is_successful: bool
   - RepositoryParseResult(BaseModel):
       * repository_id: str
       * documents: list[NormalizedDocument]

B. Parser Base Interface & Utilities (app/core/rag/parsers/base.py):
   - BaseContentParser(ABC):
       * Abstract method: parse(file: ClassifiedFile, repo_root: Path) -> ParseResult
   - read_text_safely(path: Path) -> tuple[Optional[str], Optional[str]]:
       * Tries utf-8, utf-8-sig, latin-1, cp1252 encodings.
       * Returns (content, error_message) cleanly without raising unhandled exceptions.

C. Source Code Parser (app/core/rag/parsers/code_parser.py):
   - SourceCodeParser(BaseContentParser):
       * Reuses Tree-sitter ParserRegistry from app/core/parser/registry.py.
       * Parses classes, methods, and functions into discrete NormalizedDocument records.
       * Sets exact 1-indexed start_line and end_line slices from the source file.
       * Populates symbol (unique AST symbol ID) and section (e.g. 'class AuthService', 'method AuthService.validate').
       * Extracts docstring, parameters, return_type, and calls into metadata.
       * For script-like code or languages without Tree-sitter grammars (HTML, CSS, Shell, SQL, Rust),
         gracefully extracts module-level documents with accurate line ranges.

D. Markdown Parser (app/core/rag/parsers/markdown_parser.py):
   - MarkdownParser(BaseContentParser):
       * Uses regex heading matching while ignoring markdown comments and lines within ``` code blocks.
       * Builds hierarchical breadcrumbs across heading levels:
         e.g., 'CodeSpec AI > Architecture > Graph Engine'.
       * Emits NormalizedDocument per section with exact line ranges.
       * Captures introductory text preceding the first heading as 'Overview' section.
       * Flat Markdown files without headings produce a single 'document' section.

E. PDF Parser (app/core/rag/parsers/pdf_parser.py):
   - PdfParser(BaseContentParser):
       * Uses pypdf.PdfReader isolated behind the interface.
       * Iterates page by page: sets page_number = idx + 1 (1-indexed).
       * Captures page text, total page count, and section = 'Page N'.
       * Isolates corrupted, encrypted, or empty PDFs, recording a structured ParserError
         without crashing ingestion.

F. Plain Text Parser (app/core/rag/parsers/text_parser.py):
   - PlainTextParser(BaseContentParser):
       * Reads plain text (.txt, .log, .rst, etc.) using safe multi-encoding fallback.
       * Sets start_line = 1 and end_line = total_lines, section = 'text'.

G. Configuration Parser (app/core/rag/parsers/config_parser.py):
   - ConfigParser(BaseContentParser):
       * Handles JSON, YAML, TOML, INI, CFG, Dockerfile, Makefile, Procfile.
       * For INI/CFG: splits by [section] headers, preserving section-level line ranges.
       * For JSON/YAML: extracts top_level_keys into metadata.
       * Never crashes on malformed syntax; logs SyntaxWarning error while preserving raw document.

H. Content Parsing Service (app/core/rag/parsers/service.py):
   - ContentParsingService:
       * Maps FileType to the corresponding parser instance.
       * parse_file(file, repo_root): Catches all unexpected exceptions and records
         Structured ParserErrors, guaranteeing zero ingestion crashes.
       * parse_repository(files, repo_root): Iterates over all processable files,
         aggregating all NormalizedDocument instances, recording errors, and returning
         a typed RepositoryParseResult.

4. PHASE 3: SEMANTIC CHUNKING [STATUS: COMPLETED]
================================================================================

4.1 Objectives & Deliverables
------------------------------
  - Create a unified chunking service producing retrieval-ready chunks from
    normalized repository content.
  - Implement content-aware chunking strategies:
      * 1. Source code: Prefer function/method/class boundaries, preserve symbol
           and line ranges, avoid splitting functions unnecessarily.
      * 2. Markdown/documentation: Prefer heading/section boundaries, preserve
           section hierarchy breadcrumbs.
      * 3. PDF: Preserve 1-indexed page numbers, chunk extracted text semantically.
      * 4. Plain text / config: Sensible text chunking with overlap where appropriate.
  - Deliverable Requirements Fulfilled:
      * Unique deterministic chunk_id for every chunk.
      * Full source traceability (repository_id, file_path, file_type, language,
        start_line, end_line, page_number, section, symbol, parent_metadata).
      * Configurable chunk size and overlap (ChunkingConfig).
      * Zero unnecessary duplication of content.
      * Filter out empty or meaningless chunks (< min_chunk_size).
      * Chunk model designed for vector database ingestion (with optional embedding
        and to_vector_payload() method).
      * Fully decoupled from embedding and retrieval.

4.2 Components & Implementation Details
---------------------------------------

A. Retrieval Chunk Model (app/models/chunk_models.py):
   - RAGChunk(BaseModel):
       * chunk_id: str - Deterministic hash (repo_id + file_path + anchor + index + digest)
       * repository_id: str - Target repository identifier
       * file_path: str - Normalized relative path with '/'
       * file_type: FileType - Category enum
       * language: Optional[str] - Programming or format language
       * content: str - Payload text/code
       * start_line: Optional[int] - 1-indexed start line
       * end_line: Optional[int] - 1-indexed end line
       * page_number: Optional[int] - 1-indexed page number (for PDFs)
       * section: Optional[str] - Heading breadcrumb or class/function scope
       * symbol: Optional[str] - AST symbol identifier
       * chunk_index: int - Sequential index within the parent document (0, 1, 2...)
       * total_chunks: int - Total chunks from the parent document
       * char_count: int - Length of content in characters
       * token_count: int - Estimated tokens (~4 chars / token heuristic)
       * parent_metadata: dict[str, Any] - Preserved AST and document metadata
       * embedding: Optional[list[float]] - Reserved for vector embedding (Phase 4)
       * to_vector_payload() -> dict[str, Any] - Ready for vector database ingestion
   - ChunkingResult(BaseModel):
       * repository_id: str
       * total_documents_processed: int
       * total_chunks_produced: int
       * chunks: list[RAGChunk]
       * chunks_by_type: dict[str, int]
   - Re-exported in app/models/__init__.py.

B. Configurable Chunking Parameters (app/core/rag/chunking/config.py):
   - ChunkingConfig(BaseModel):
       * chunk_size: int = 1000 - Target characters for general text/markdown/pdf/config
       * chunk_overlap: int = 150 - Overlap between partitioned segments
       * min_chunk_size: int = 20 - Minimum characters for valid non-empty chunks
       * code_chunk_size: int = 1500 - Leeway threshold for functions/classes before splitting
       * code_chunk_overlap: int = 200 - Line-based character overlap when splitting oversized code
       * estimate_tokens(text: str) -> int - Robust token count estimator

C. Semantic Chunking Service (app/core/rag/chunking/service.py):
   - SemanticChunkingService:
       * Deterministic Chunk ID Generator:
         format: {file_path}:{anchor}:{chunk_index}:{hash_digest}
         guarantees stable, reproducible IDs across identical ingest runs.
       * _chunk_source_code:
         If code <= code_chunk_size, emits 1 atomic chunk preserving exact symbol,
         section, start_line, and end_line without unnecessary splitting.
         If oversized, splits along lines with line-based overlap, recalculating
         start_line and end_line for every slice.
       * _chunk_markdown:
         If section <= chunk_size, emits 1 chunk preserving the full breadcrumb.
         If oversized, splits on paragraph breaks (\n\n) then sentences, preserving
         the section breadcrumb on every resulting chunk.
       * _chunk_pdf:
         If page text <= chunk_size, emits 1 chunk with page_number.
         If oversized, splits semantically, preserving page_number on every chunk.
       * _chunk_text_or_config:
         Splits recursively by delimiters (\n\n, \n, ;, ,, space) with overlap.
         Preserves INI sections and config metadata.
       * Filter:
         Drops any chunk shorter than min_chunk_size, preventing noise.
       * chunk_documents(documents, repository_id):
         Batch processor returning full ChunkingResult.

5.1 Objectives & Deliverables
------------------------------
  - Embed RAG chunks generated in Phase 3 and persist them in a vector store for
    semantic retrieval.
  - Reused existing infrastructure: Neo4j 5 native vector indexes (no duplicate
    database containers introduced).
  - Implemented pluggable embedding service abstraction (Mock, OpenAI, Gemini).
  - Implemented pluggable vector store abstraction (Neo4jVectorStore, InMemoryVectorStore).

5.2 Components & Implementation Details
---------------------------------------

A. Vector Models (app/models/vector_models.py):

7. PHASE 6: HYBRID RETRIEVAL [STATUS: COMPLETED]
================================================================================

7.1 Objectives & Deliverables
------------------------------
  - Implement a unified retrieval pipeline combining semantic vector search and Neo4j
    graph retrieval into a single HybridRetriever service.
  - Architecture Flow:
      User Query
         ↓
      Query preprocessing (symbol & file candidate extraction)
         ↓
      Vector retrieval ─────┐
                            ├──> Result fusion, deduplication & ranking (RRF / Weighted)
      Graph retrieval ──────┘
         ↓
      Top relevant ranked context
  - Perform repository-scoped vector search via IndexingService.similarity_search.
  - Identify useful files, symbols, and entities from vector hits and preprocessed query.
  - Use those seeds to perform relevant Neo4j graph expansion via GraphRetriever.
  - Merge vector and graph results and remove duplicates using canonical entity keys.
  - Rank results using configurable strategies (Reciprocal Rank Fusion / RRF or Weighted Linear).
  - Preserve rich source metadata and provenance (sources: vector, graph, hybrid; raw scores, ranks, relationships).
  - Return a typed RetrievalResult model containing a ranked list of RetrievedItem models.
  - Configurable parameters: top_k, vector_top_k, vector_min_score, graph_expansion_depth,
    graph_limit_per_seed, ranking_strategy, vector_weight, graph_weight, rrf_k.
  - Strictly enforce multi-tenant repository isolation: filter out any cross-repository leaks.
  - Gracefully handle vector store or Neo4j outages (fallback to single available source).
  - Keep the retrieval layer decoupled from FastAPI routes and do not call LLMs yet.
  - Comprehensive unit testing across all operational and edge scenarios.

B. Hybrid Retrieval Service (app/core/rag/retrieval/hybrid_retriever.py):
   - HybridRetriever:
       * Coordinates IndexingService and GraphRetriever.
       * query(query, repository_id, config=None) -> RetrievalResult
   - Pipeline Execution Steps:
       1. Validation: Checks non-empty query and repository_id.
       2. Query Preprocessing: Uses regex to extract potential symbols (CamelCase, snake_case,
          dotted symbols) and file paths (.py, .ts, etc.) from query text to act as direct graph seeds.
       3. Vector Retrieval: Queries vector store strictly scoped to repository_id.
       4. Graph Expansion: Collects seeds from top vector hits and query candidates. Expands
          each seed via GraphRetriever.get_symbol_context() and get_file_context().
       5. Fusion & Deduplication: Groups candidates by canonical key (file_path::symbol or
          file_path::chunk_id). Overlapping candidates are merged into "hybrid" items with
          dual provenance and enriched metadata.
       6. Ranking:
          - Reciprocal Rank Fusion (RRF): score = sum(weight / (k + rank)).
          - Weighted Linear: score = w_vec * vector_score + w_graph * graph_score.
       7. Repository Isolation: Strictly verifies item.repository_id == repository_id.
       8. Fault Tolerance: Vector store failures fall back gracefully to graph retrieval;
          Neo4j failures fall back gracefully to vector search; neither crashes the pipeline.

        and documentation section.
      * Removes duplicate and redundant retrieval results (exact content matches and
        span subsumption where a broader line range encompasses a narrower one).
      * Enforces configurable context/token limits (max_context_chars, max_tokens)
        with graceful truncation.
  - Create an end-to-end RAG orchestration service (RAGService):
      * Pipeline flow:
          query
            ↓
          HybridRetriever
            ↓
          ContextBuilder
            ↓
          BaseLLMProvider (LLMService)
            ↓
          RAGResponse
  - Grounding & Anti-hallucination Prompting:
      * STRICT_RAG_SYSTEM_PROMPT directs model to answer ONLY using supplied context.
      * Prohibits inventing or extrapolating repository facts.
      * Mandates explicit fallback prefix ("INSUFFICIENT CONTEXT: ...") when the retrieved
        context is inadequate.
      * Requires bracket citations ([1], [2]) mapped to concrete source items.
  - Return typed, structured RAGResponse containing:
      * answer: str
      * sources: list[RAGSourceItem] with full provenance
      * retrieval_metadata: RAGMetadata (timing, counts, provider, model)
      * is_insufficient_context: bool flag detecting lack of context
  - Keep orchestration 100% provider-agnostic (works with Mock, OpenAI, Gemini, Ollama).
  - Robust error handling (strict mode vs. non-strict graceful degradation).
  - Comprehensive unit testing across all key behaviors.

C. ContextBuilder Service Enhancements (app/core/rag/generation/context_builder.py):
   - Deduplication Engine (_deduplicate_items):
       * Exact Content Matching: Hashes normalized item content to discard identical chunks.
       * Line Range Subsumption: If an item shares the same file_path and symbol, checks whether
         its line range is fully enclosed by an already-included item.
   - Provenance Header Formatting:
       * Builds structured headers for each context item:
         --- Context Item [1] ---
         Repository: <repo_id> | File: <file_path> | Type: <file_type>
         Symbol: <symbol> | Lines: <start>-<end> | Page: <page> | Section: <section>
         Score: 0.85 | Sources: vector, graph
         Graph relationships: [relationships if any]
         ```<lang>
         <content>
         ```
   - Budget Management:
       * Respects max_context_chars and max_tokens.
       * Truncates oversized items with [Content truncated to fit token budget...] notices.
   - Anti-Hallucination Grounding Prompt (STRICT_RAG_SYSTEM_PROMPT):
       * Directs the LLM to act as a precise repository code intelligence assistant.
       * Explicitly forbids inventing files, methods, parameters, or behaviors not in context.
       * Mandates prefixing answers with "INSUFFICIENT CONTEXT: ..." when the repository context
         does not contain the necessary information.
       * Enforces bracket citation tags ([1], [2]) linking statements directly to source items.

D. RAG Service Orchestrator (app/core/rag/generation/rag_service.py):
   - RAGService:
       * Coordinates query -> HybridRetriever -> ContextBuilder -> BaseLLMProvider -> RAGResponse.
       * Measures fine-grained timing for retrieval, generation, and total pipeline execution.
       * Detects insufficient context keywords ("insufficient context", "not enough context",
         "cannot answer based on the provided context") to automatically set
         RAGResponse.is_insufficient_context = True.
       * Exception Handling:
           - In strict=False mode (default): returns graceful RAGResponse with is_successful=False
             and descriptive error_message.
           - In strict=True mode: re-raises underlying exceptions for caller-level handling.
   - Convenience function:
       * query_rag(query, repository_id, **kwargs) -> RAGResponse.
